# The documentation site

The site at [agenticterms.integraledger.com](https://agenticterms.integraledger.com): a [Fumadocs](https://fumadocs.dev)
app on Next.js, exported as static files and served by Cloudflare as a Worker's static assets.

It holds no documentation of its own. Its pages are the repository's [`docs/`](../docs), read in place, and API pages that
TypeDoc generates from the packages' TypeScript source at every build.

## What it serves

| Path | What it is |
| --- | --- |
| `/`, `/<page>` | Every page of `docs/`, with its sidebar order from each folder's `meta.json`. A request whose `Accept` header prefers `text/markdown` gets the page as Markdown. |
| `/api/terms`, `/api/terms-mcp` | The API reference, generated by TypeDoc from `agentic-terms/src` and `agentic-terms-mcp/src`. |
| `/llms.txt` | The index of every page, for AI agents ([llmstxt.org](https://llmstxt.org)): the versions the pages document, where the protocol is documented, the rules an agent must not miss, then each page as Markdown in sidebar order, each section led by its own file with its size, then the gate's profile, vectors and skill. `src/lib/llms-files.ts` writes it. |
| `/llms-full.txt`, `/guides/llms-full.txt`, `/reference/llms-full.txt`, `/api/llms-full.txt` | Every page as Markdown, in one file, and the pages of each section (`SECTION_FILES` in `src/lib/llms.ts`). |
| `/<page>.md`, `/index.md` | One page as Markdown, at its address with `.md` appended: its title, description and address, the date it last changed, the versions it documents and `/llms.txt`, then its body, with each link to a page of the site, or to a profile, vector file or skill in a repository, rewritten to the Markdown or JSON a site serves for it. The build writes each page's copy at `/md/<page>.md`. |
| `/profiles/<name>.md`, `/vectors/<name>.json` | The gate's profile and vector files, byte for byte from `agentic-terms/profiles/` and `agentic-terms/vectors/`. |
| `/.well-known/agent-skills/index.json`, `/.well-known/agent-skills/<name>/SKILL.md` | The MCP server's skill, byte for byte from `agentic-terms-mcp/skills/`, and the index that names it with its SHA-256. |
| `/og/<page>/image.png`, `/og/image.png` | Each page's social card, 1200×630, written at build time in Geist. |
| `/twoslash/<page>.json` | A page's Twoslash popups, fetched when a reader first opens one. |
| `/api/search` | The static search index. |
| `/sitemap.xml`, `/robots.txt` | For crawlers: every crawler is allowed, with `Content-Signal: search=yes, ai-input=yes, ai-train=yes`. |
| `/.well-known/security.txt` | Where to report a vulnerability ([RFC 9116](https://www.rfc-editor.org/rfc/rfc9116)), under [`SECURITY.md`](../SECURITY.md). It expires 180 days after the commit the site is built from. |

Every TypeScript sample is type-checked by [Twoslash](https://twoslash.netlify.app) against the packages as they are
built in this repository, and the build fails on a type error. Hovering, focusing or clicking an identifier shows its
type and documentation: the build writes each page's distinct popups to `/twoslash/<page>.json`, which the page fetches
when a reader first opens one.

Each ```` ```mermaid ```` block is rendered to SVG at build time with the `mermaid` package, in a pinned Chrome Headless
Shell, once in a light and once in a dark theme. Every text is measured and drawn in Inter, from the
`@fontsource-variable/inter` package, and in no font of the machine's: the browser has a font configuration of its own
with no font in it, and its clock reads UTC and formats in the en-US locale. A diagram with a character Inter does not
draw fails the build. Both SVGs are in the page's HTML, and the page shows the one for the reader's theme; the site
serves the same Inter files, and no diagram code runs in the browser.

## Building

The site reads the built packages, so build them first, from the repository root:

```sh
pnpm install --frozen-lockfile
pnpm -r --if-present run build
```

Then, in this folder, which has its own lockfile and install policy:

```sh
pnpm install --frozen-lockfile
pnpm run browser   # fetch the browser that draws the Mermaid diagrams into .browser/, checked by its SHA-256
pnpm run build
```

The diagrams are drawn in one browser build: Chrome Headless Shell 156.0.8078.4 for Linux x64, the build the locked
`playwright-core` names, from Chrome for Testing's
[download bucket](https://googlechromelabs.github.io/chrome-for-testing/). `scripts/browser.mjs` holds its version, its
address and the SHA-256 of its archive; `pnpm run browser` fetches the archive, retrying five times after a network
error or an answer other than 2xx, checks it and unpacks it. The build uses no other browser: on a machine without it,
it stops and names that command.

The site is built on Linux x64, in CI or on a maintainer's Linux x64 machine. The browser build is pinned for that one
platform because a build for another platform measures text through that platform's own font engine, so its diagrams
could differ; on another platform the build stops and names the platform it is pinned for.

`node scripts/check-highlighting.mjs`, after the build, checks that the code highlighting gives one result however
long tokenizing takes, in the themes' colours, and that no other source highlights code.

`node scripts/check-diagrams.mjs`, after the build, draws every diagram again under a font configuration that changes
every font's rendering and checks that the SVGs are the same, that a diagram with a character Inter does not draw is
refused, and that `out/` serves the Inter files the diagrams are drawn in.

Once the browser is in `.browser/`, the build reads nothing from the network. The social cards are drawn in Geist, the
font next/og bundles, alone: a page whose title or description holds a character Geist does not draw stops the build,
naming the character, where next/og would fetch a font from Google Fonts or an emoji from Twemoji. `next.config.ts`
turns off the upgrade check `next build` makes of the npm registry, and the `build` script empties
`__NEXT_AGENT_UPGRADE`, the environment variable that turns the check on whatever the configuration says. The script
sets `NEXT_TELEMETRY_DISABLED=1`, since Next.js has no configuration for its telemetry.

After `next build`, the `build` script writes each page's script policy (`scripts/script-policy.mjs`): a `<meta
http-equiv="Content-Security-Policy">`, the first element of the page's `<head>` after its character encoding, whose
`script-src` names `'self'` and the SHA-256 of each inline script the page holds. A static export carries no nonce, and
the hashes of one page run past the 2,000 characters a line of `public/_headers` may hold, so each page carries its own
policy. The browser applies it together with the one `public/_headers` sets, so an inline script runs only when its
page's policy names it. `node scripts/check-script-policy.mjs`, after the build, parses every page in the pinned browser
and checks that each holds one such policy, first in its head after the character encoding, naming each inline script
the page holds and no other, and that no page holds an event handler attribute or a `javascript:` URL, which such a
policy refuses.

Every response that is not a page takes a second header policy, `default-src 'none'; script-src 'none'`, which
Cloudflare joins to the first with a comma: the browser enforces both, so a file opened as a document, an SVG image
above all, runs no script. `check-script-policy.mjs` also checks that `public/_headers` keeps within Cloudflare's 100
rules and 2,000 characters a line, that every file of `out/` that is not a page, and each page's `.md` address, takes
that policy and no page address does, and, serving `out/` with those headers, that every page loads with no policy
violation and refuses an inline script added to it, and that an inline script added to each SVG and XML file runs when
the file is opened without the headers and is refused with them.

Last, the `build` script runs `scripts/check-llms.mjs`: every link of the site's own in `/llms.txt` names a file of
`out/`, each size it states is that file's, it lists every page's Markdown copy and each copy names it, and
`/.well-known/agent-skills/index.json` names each skill at its file with that file's SHA-256.

The static site is in `out/`. `public/_headers` sets its response headers, and `wrangler.toml` deploys `out/` as a
Worker's static assets with the site's 404 page. `pnpm run dev` serves it locally while you edit `docs/`; it does not
run `worker.js`.

## How it is served

`wrangler.toml` serves `out/` as a Worker's static assets, with `worker.js` in front of the page addresses and their
`.md` addresses only:

- `/<page>.md`, and `/index.md` for the home page, answer with the page's Markdown copy (the address
  [llmstxt.org](https://llmstxt.org) proposes). `/llms.txt` links each page there. A `.md` address that names no page
  is answered 404 in Markdown that names `/llms.txt`.
- A request for a page whose `Accept` header ranks `text/markdown` (or `text/x-markdown`) at least as high as
  `text/html` gets the same Markdown at the page's own address; `text/plain` is not a Markdown type and gets HTML. A
  page address that ends in a slash redirects to the address without it, for Markdown as for HTML. Every response for
  a page address carries `Vary: Accept`, and a conditional request for a Markdown copy can be answered 304.
- Every other file is served directly, without the Worker: the Markdown copies, the profile, vector and skill files,
  the scripts, the search index and every `.txt` file, the RSC payload each page fetches among them.

Cloudflare applies `public/_headers` to the files it serves directly, but not to a response a Worker returns
([Headers](https://developers.cloudflare.com/workers/static-assets/headers/)). So `worker.js` sets, on every response
it returns, the headers `public/_headers` gives the request's path, each replacing any value the response holds:
`headers.mjs` reads them from the file, which `wrangler.toml` bundles into the Worker as a text module.
`public/_headers` is their one source. `node scripts/check-worker.mjs`, after the build, runs `worker.js` against
static assets that answer with no header and against ones that answer with their own, and checks that each kind of
response it returns carries those headers, once each.

Each page names `/llms.txt` with `<link rel="describedby">` and its Markdown with `<link rel="alternate"
type="text/markdown">`, and names both in a line of its body, for an agent that reads the page as text. The same links
go in HTTP `Link` headers: `public/_headers` gives every path `</llms.txt>; rel="describedby"`, and `worker.js` adds the
page's Markdown address (`rel="alternate"; type="text/markdown"`) to a page's HTML and the page itself
(`rel="canonical"`) to its Markdown at its `.md` address. The copies at `/md/` carry `X-Robots-Tag: noindex`: they are
what the pages' copy buttons fetch, and the `.md` address is the one to cite.

## Deploying

No workflow deploys the site. The site documents the packages npm and PyPI serve, so a maintainer deploys it by hand
from the commit each release is built from: check that commit out, build the packages and the site on Linux x64 (see
"Building"), and run, at the repository root:

```sh
npx wrangler deploy -c website/wrangler.toml
```

`/.well-known/security.txt` expires 180 days after that commit, so each release's deploy renews it.

Then, in this folder, check the headers the deployed site answers with:

```sh
node scripts/check-live-headers.mjs https://agenticterms.integraledger.com
```

It requests a page, that page's `.md` address, `/icon.svg` and an address no file has, with and without `.md`, and
checks each status and that each response carries every header `public/_headers` gives its path, with that value and
the `Link` the Worker adds. It names each header that
differs and exits 1. `scripts/check-worker.mjs` runs it against a server of `out/` that answers as Cloudflare does.
